# Sambahamphe Community Platform — Monorepo Guidelines

Digital heritage platform for Sambahamphe Utthan Sangh: genealogy, organizational boards, heritage content, events and media. Managed with **pnpm workspaces** + **Turborepo**.

## Read first

- **Product decisions are binding:** [docs/product/genealogy-access-policy.md](docs/product/genealogy-access-policy.md), [docs/product/member-registration-flow.md](docs/product/member-registration-flow.md), and the decisions table in [docs/product/requirements.md §7](docs/product/requirements.md).
- **Design:** [docs/architecture/system-design.md](docs/architecture/system-design.md), [docs/architecture/architecture-decisions.md](docs/architecture/architecture-decisions.md) (ADRs), [docs/database/schema-design.md](docs/database/schema-design.md), [docs/api/api-conventions.md](docs/api/api-conventions.md).
- **App-specific rules** live in `apps/<app>/CLAUDE.md` (and `packages/<pkg>/CLAUDE.md`). Read the relevant one before working in that workspace — its rules are blocking.
- When a design decision changes, update the doc and ADR in the same change. Docs must not drift from code.

## Layout

```
apps/
  api/        # NestJS REST API + BullMQ worker (same build, two entrypoints)
  web/        # Next.js public site (SSR, SEO-critical)
  admin/      # Next.js CMS
  mobile/     # Expo (Phase 5)
packages/     # shared libraries, all named @repo/<name>
  config/     # eslint / prettier / tsconfig presets
  contracts/  # Zod schemas = API request/response contracts
  api-client/ # typed client generated from OpenAPI
  dates/      # FuzzyDate + Bikram Sambat ↔ AD conversion
  ui/         # shared React components
infrastructure/  # Dockerfiles, compose.prod, Caddy, backup scripts, runbooks
docs/
```

Packages under `packages/` are compiled to `dist/` (ESM) and consumed from there; Turborepo builds them before anything that depends on them (`dependsOn: ["^build"]`). After changing an endpoint or contract, run `pnpm openapi:generate` and commit the spec.

Run workspace commands with `pnpm --filter <name> <script>`. Root scripts (`pnpm dev`, `build`, `lint`, `typecheck`, `test`, `format`, `check`) run through Turborepo.

## Repo-wide rules (blocking)

### Workspace & dependencies

- **No app code at root.** Root holds only workspace config, CI and tooling.
- **Per-workspace `package.json`.** Only `turbo` and repo-wide tooling (husky, commitlint) go in the root `package.json`. **One lockfile**, at the root.
- **Versions come from catalogs** in `pnpm-workspace.yaml` (`catalog:generic`, `catalog:fe`, `catalog:be`). Never write a literal version in a `package.json`; add the dependency to a catalog, then reference `"catalog:<name>"`.
- **`packages/*` use `peerDependencies`**, never `dependencies`; the consuming app installs the concrete version. Apps own their full dependency tree.

### TypeScript

- `strict`, `noUnusedLocals`, `noUnusedParameters`. Prefix intentionally unused params with `_`.
- **No `any`** (`@typescript-eslint/no-explicit-any: error`). If one is truly unavoidable, a comment must say why.
- Interfaces are prefixed `I` (`IPersonNode`), type aliases `T` (`TLineageRole`). Types inferred from Zod follow the same rule (`type TFuzzyDate = z.infer<typeof fuzzyDateSchema>`).
- Use `satisfies` to type-check without widening.
- **Named exports only** — never `export default` (framework files that require a default export, such as Next.js `page.tsx`/`layout.tsx`, are the only exception).

### Helpers are classes with static methods

Any utility, helper or non-React `lib` file exposes its functions as static methods on one class. The file is `<name>.helper.ts` and the class mirrors it (`fuzzy-date.helper.ts` → `FuzzyDateHelper`).

```ts
// Correct
export class SlugHelper {
  static fromText(input: string): string { ... }
}

// Wrong
export function slugify(input: string) { ... }
```

A truly local one-liner should be inlined instead of becoming a helper file.

### No magic values

Timeouts, limits, depths, page sizes, retry counts, query keys, storage keys and route paths come from a named constant or config, never a bare literal inside a call. Example: the tree-depth cap is `TREE_MAX_DEPTH`, not `6`.

### Comments: only where the code can't speak for itself

The default is **no comment**. Never write a comment that describes what a declaration is or does — the name already says it. Comment only a non-obvious *why*: an edge case, a constraint, a business rule, a workaround.

```ts
// Wrong — restates the code
/** Returns the person's ancestors. */
static ancestors(...) { ... }

// Correct — states what the code cannot
// Unknown living status with no dates counts as living: deny-by-default (ADR-021).
```

- No AI-authorship comments (`// generated by…`, `// added by Claude`).
- No commented-out code, no `console.log` left in a diff.
- One terse line beats a block. Never leave a half-edited comment.

## Domain rules (blocking — these protect the archive)

### Privacy of living people

- Every response containing person data passes through the people module's **privacy policy** before serialization. Response schemas then strip anything not declared.
- **No viewer context means the most restrictive view.** A script, job or export without a viewer must never be the path that leaks data.
- Never cache a *privacy-filtered* person response in a shared cache — the result depends on the viewer. Cache the raw data and filter per request.
- Exports (GEDCOM/CSV), search, sitemaps and JSON-LD follow the same policy. Minors follow ADR-023.
- Never log names, dates of birth, phone numbers or emails. The logger redacts known fields; do not work around it.

### Genealogy integrity

- Genealogy writes go **only** through change requests (ADR-012), including editors' direct edits (auto-approved).
- Never hard-delete or overwrite approved genealogy records. Use status changes (`retracted`, `superseded`, `merged`) and keep revisions.
- Versioned records are updated with the expected `version` (optimistic concurrency); a mismatch is `409`, never a silent overwrite.
- Male-line rules (ADR-020) are enforced in the genealogy service inside the write transaction, not only in the UI.

### Dates

Historical dates are `FuzzyDate` values (calendar BS/AD, qualifier, precision). Never display a raw date. Format through `@repo/dates` so BS and AD render consistently on every client.

### Images are full media objects

Any image in an API response is the full media object — `id`, `url`, `width`, `height`, `blurHash`, `alt` — never a bare URL. Clients need the dimensions and blurhash to avoid layout shift and to show placeholders on slow connections.

## Backend (`apps/api`) patterns

Detailed rules go in `apps/api/CLAUDE.md` when the app is created. The core shape:

- **Controller → Service → Repository.** Controllers are thin: validate, authorize, delegate, return. Services hold the business logic and transactions. Repositories are the only layer that talks to the database.
- **DTOs:** schemas come from `@repo/contracts`. One DTO per file: `<action>-<resource>.request.dto.ts`, `<resource>.response.dto.ts`. Services return data **parsed through the response schema**.
- **Errors:** throw typed exceptions with a stable `code`. The global filter renders RFC 9457 problem+json (see API conventions). Never leak raw database errors.
- **Database (Drizzle, ADR-003):** one schema file per table (`<table>.schema.ts`), re-exported from `schema/index.ts`; camelCase in TypeScript, snake_case in the database.
- **Migrations:** always named (`drizzle-kit generate --name=add_branch_access`, snake_case, describing the change). Generated DDL is never hand-edited. Constraints Drizzle cannot express (exclusion constraints, some checks, triggers, SQL functions) go in a **custom migration** (`drizzle-kit generate --custom --name=…`), are listed in `schema-design.md` §13 and are covered by an integration test.
- **Raw SQL** only through Drizzle's `sql` template (parameterized); never string-built.

## Frontend (`apps/web`, `apps/admin`) patterns

Detailed rules go in each app's `CLAUDE.md` when it is created. The core shape:

- **Feature folders:** `src/features/<Feature>/{components,hooks,types.ts}`. Promote to shared `src/components/` only when 2+ unrelated features use it.
- **Route files are thin wrappers.** The page component lives in its feature.
- **One component, hook or class per file.** Skeletons and sub-components get their own file.
- **Components and hooks are function declarations**, never `const X = () => …`.
- **Props are a named `interface <Component>Props`** above the component — never an inline object type, however small.
- **Tailwind: theme tokens only.** No raw palette colors (`bg-gray-100`), no arbitrary values (`w-[200px]`), no inline `style` except runtime-computed values. A missing token is added to the theme first.
- **Conditional classes through `cn()`** (clsx + tailwind-merge), never template literals.
- **No hardcoded user-visible strings.** All copy goes through the i18n messages (`en`, `ne`), with keys in `snake_case` prefixed by feature.
- **React-first:** refs, state and hooks instead of `document.querySelector` or manual DOM mutation.
- **Destructive actions require a confirmation dialog** (admin especially: retracting relationships, revoking access).
- **Public pages fetch first-paint data on the server**, so the SSR HTML is complete (SEO).

## Workflow

- **Branches:** `develop` is the main branch. While there is a single contributor, work happens on **one branch per roadmap milestone** (`feat/m1.3-auth`), not per small feature or fix. Open a **draft PR into `develop` as soon as the branch exists** so CI runs on every push, and merge when the milestone is done. Switch to short-lived per-feature branches once other contributors join.
- **Commits:** Conventional Commits, `type(scope): summary` (enforced by commitlint). Scope is the workspace or domain: `feat(genealogy): …`, `chore(config): …`. No AI co-author trailers or "generated with" lines in commits or PRs.
- **One milestone per PR, one logical step per commit.** Keep commits small and self-contained inside the milestone branch so any step can be reverted alone. Fill in the PR template; mark sections that don't apply as `N/A — <reason>`.
- **Before calling work done:** typecheck, lint and tests pass for affected workspaces, and the behavior was actually exercised. Never report a check as passing unless it was run.
